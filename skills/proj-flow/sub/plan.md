# 需求整理与排序 — 六步工作流

> 此文件为 `proj-flow` skill 的子组件。Agent 在收到需求排序类触发词后应读取此文件。
> 共享纪律（neat-freak、git commit、上下文压缩、阶段命名、复杂度评分）详见 `sub/shared.md`。

---

## 概述

当你收到混合的需求列表（新功能 + Bug修复 + 问题澄清）时，按以下标准化工作流将其拆解为有序执行计划。

**核心能力**：
- **拆解**：从自然语言消息中提取独立条目
- **分类**：三级分类（新增需求 / Bug修复 / 问题澄清）
- **依赖分析**：前后端依赖、数据流依赖、代码依赖识别
- **复杂度评分**：1-5 星量化任务难度（详见 shared.md 第四章）
- **排序输出**：按依赖拓扑 + 由简到难生成执行计划

---

## 工作流（6 步）

### 第一步：读取并拆解

从用户消息中提取所有独立条目，每条为独立一句/一段：

```
用户消息示例：
"数据导出按钮点击没反应。
 列表页筛选后有重复数据。
 需要支持批量删除功能。"

→ 拆解为 3 条独立条目：
  1. 数据导出按钮无响应
  2. 列表筛选后数据重复
  3. 批量删除功能
```

### 第二步：三级分类

对每条拆解后的条目归档：

| 分类 | 标识 | 判断标准 | 示例 |
|------|------|---------|------|
| **新增需求** | `[NEW]` | 当前不存在的功能、增强 | "支持批量删除功能" |
| **Bug修复** | `[FIX]` | 已有功能行为不符合预期 | "导出按钮点击没反应" |
| **问题澄清** | `[Q]` | 用户不确定、需要说明流程 | "如何手动测试导出功能" |

> **规则**：`[Q]` 类不产生代码改动，仅在执行计划末尾输出说明文档。

### 第三步：依赖分析

对 `[NEW]` 和 `[FIX]` 条目，分析相互依赖关系：

| 类型 | 说明 | 判断方法 |
|------|------|---------|
| **前后端依赖** | A 改前端 → 依赖 B 改后端接口 | 涉及同一 API 的前后端文件 |
| **数据流依赖** | A 改数据 → B 消费这个数据 | 数据模型变更 → 渲染消费方 |
| **代码依赖** | A 改组件 → B 继承/复用 A | 共享组件、工具函数修改 |
| **无依赖** | 完全独立 | 修改不同文件、不同模块 |

**分析输出格式**：

```
任务A [FIX] 导出按钮无响应
  → 任务B [FIX] 导出文件名乱码（依赖A：同模块）
任务C [FIX] 列表筛选重复数据
  → 无依赖
任务D [NEW] 批量删除功能
  → 无依赖（独立模块）
```

### 第四步：复杂度评分

每条任务按 1-5 分评估复杂度，评分标准详见 `sub/shared.md` 第四章「复杂度评分」。

### 第五步：排序输出执行计划

#### 排序规则

1. **按依赖拓扑排序**：无依赖的排前面，被依赖的排前面
2. **同依赖层级内按复杂度升序**：简单的先做（由简到难）
3. **`[Q]` 类永远排在最后**（纯文档输出，不阻塞开发）

#### 输出格式

使用 `todo_write` 的 JSON 结构输出（ID 规范详见 `sub/shared.md` 第四章）：

```json
[
  {"id": "stage_N", "content": "阶段N：阶段名称", "status": "PENDING"},
  {"id": "task_1", "content": "任务1 [FIX] 简短描述 (依赖：无) ⭐", "status": "PENDING"},
  {"id": "task_2", "content": "任务2 [FIX] 简短描述 (依赖：任务1) ⭐⭐", "status": "PENDING"},
  {"id": "task_3", "content": "任务3 [NEW] 简短描述 (依赖：无) ⭐⭐⭐", "status": "PENDING"}
]
```

#### 阶段划分建议

| 阶段 | 条件 |
|------|------|
| 快速修复 | 复杂度 ≤2 且无依赖的 `[FIX]` 任务 |
| 页面优化 | 同页面/同模块的前端改动聚合 |
| 后端修复 | 后端路由/服务层纯后端改动 |
| 功能升级 | `[NEW]` 类新功能 |
| 收尾 | `[Q]` 类说明 + 全量回归测试 |

#### 每个阶段末尾必须提醒用户

```
→ neat-freak 文档同步
→ git commit: "一句话中文总结本轮改动"
```

> neat-freak 联动规则和 git commit 纪律详见 `sub/shared.md`。

### 第六步：执行纪律

Agent 在收到整理好的执行计划后，必须遵守：

1. **按顺序执行**：不跳任务、不改顺序（除非用户明确要求）
2. **子任务组完成**：每完成一组有依赖关系的任务 → 提醒用户执行 neat-freak + git commit
3. **阶段完成**：每完成一个大阶段 → 读取 `sub/wrap.md` 执行收尾流程
4. **遇到阻塞**：如果某任务依赖的先决条件不满足，暂停并告知用户

## 使用示例

```
用户：数据导出点击没反应，列表页筛选有重复数据，详情页数据匹配不上。
      另外需要支持批量删除功能。

Agent 行为：
1. 读取 sub/plan.md（本文件）
2. 拆解为：Bug修复×2 + 新增需求×1
3. 分析依赖关系 → 按依赖排序 → 由简到难排列
4. 输出 todo_write 格式的执行计划
5. 逐一执行，每完成一组后触发 neat-freak + git commit（详见 shared.md）
```

---

## 与其他子组件的关系

- 输出执行计划后，Agent 自动进入阶段执行模式 → 读取 `sub/executing.md`
- 每个大阶段完成后 → 读取 `sub/wrap.md` 执行收尾
- 执行中用户追加减需 → 重新读取本文件重排计划

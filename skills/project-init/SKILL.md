# Project Init — 项目初始化五步工作流

## 概述

当用户启动一个全新项目（或对旧项目做彻底重构）时，按以下5步执行，确保项目落地即有清晰架构、可执行计划、和 Agent 自我管理规则。

**核心原则**：
- 每步产出至少一份文档，落盘到项目目录
- 对不确定之处，Qoder 环境用 `ask_user_question` 单选/多选澄清；非 Qoder 环境用对话式提问
- 不允许跳过步骤，但允许用户明确说"这步不需要"后跳过

---

## Step 1：需求澄清与问题分析

**目标**：产出 `docs/requirements.md`，回答"做什么、为谁做、核心流程是什么"。

### 1.1 项目性质判断

首先向用户确认：

**Qoder 环境** — 调用 `ask_user_question`：
```
question: "这是全新项目还是对旧项目的重构/迁移？"
options:
  - "全新项目" — 从零开始，无历史包袱
  - "重构旧项目" — 保留数据，重写代码
  - "迁移旧项目" — 从旧平台/旧架构迁到新方案
```

**非 Qoder 环境** — 直接问：「这是全新项目，还是重构/迁移旧项目？」

### 1.2 需求收集（3个核心问题）

逐一提问并记录答案：

| # | 问题 | 目的 |
|---|------|------|
| 1 | 这个项目解决什么核心问题？用户是谁？ | 确定项目存在价值 |
| 2 | 用户最频繁的 1-3 个操作/任务是什么？ | 提取核心流程 |
| 3 | 有没有必须对接的外部系统或服务？ | 识别外部依赖边界 |

### 1.3 输出

将收集到的信息整理为 `docs/requirements.md`，使用此结构：

```markdown
# 项目需求文档

## 项目性质
[全新项目 / 重构 / 迁移] — 一句话说明

## 核心问题与用户
- 解决的问题：
- 目标用户：

## 核心流程（≤5条）
1. [流程名称]：用户做什么 → 系统做什么 → 结果是什么
2. ...

## 外部依赖
| 外部系统 | 依赖程度 | 说明 |
|---------|---------|------|

## 非功能约束（如有）
- 性能、安全、合规、平台等特殊要求
```

## Step 2：架构设计

**目标**：产出 `docs/architecture.md`，回答"怎么做——分层、模块、数据、接口"。

### 2.1 项目类型识别

**Qoder 环境** — 调用 `ask_user_question`，单选：

```
question: "这个项目属于哪种类型？"
options:
  - "Web全栈应用" — 前后端分离（React/Vue + API + 数据库）
  - "REST/GraphQL纯API" — 仅有后端API服务，无前端界面
  - "CLI命令行工具" — 终端命令，参数输入输出
  - "库/SDK/框架" — 供其他项目引用的代码包
  - "数据处理管道" — ETL、流处理、批处理
  - "移动端App" — iOS/Android 或 React Native/Flutter
  - "静态网站/文档站" — SSG、博客、文档
  - "微服务/云函数" — Serverless 函数或微服务集群
```

然后追问技术选型（可多选）：

```
question: "技术栈选择偏好？"
multiSelect: true
options:
  - 运行时：Node.js / Python / Go / Rust / JVM / .NET
  - 数据库：SQLite / PostgreSQL / MySQL / MongoDB / Redis
  - 前端框架（如适用）：React / Vue / Next.js / 纯HTML
  - 其他关键选型由 Agent 根据项目类型推荐
```

**非 Qoder 环境** — 按序提问：项目类型 → 运行时 → 数据库 → 前端框架 → 其他关键选型。

### 2.2 按类型输出架构文档

根据项目类型，从 [templates/architecture.md](templates/architecture.md) 加载对应模板，**至少包含以下章节**：

| 项目类型 | 必须包含的章节 |
|---------|--------------|
| Web全栈 | 四层架构图、数据模型ER、API路由表、核心数据流、前后端交互协议 |
| 纯API服务 | 分层架构、数据模型ER、API路由全表、中间件链、认证方案 |
| CLI工具 | 命令树、参数设计、配置层级、I/O管道、退出码规范 |
| 库/SDK | 公开API面、模块依赖图、插件/扩展机制、版本策略 |
| 数据处理管道 | 阶段拓扑图、数据Schema演变、错误队列与重试、幂等性策略 |
| 移动App | 页面路由栈、离线存储、推送通道、平台适配方案 |
| 静态网站 | 页面路由树、数据源（MDX/API/本地）、构建流程、SEO策略 |
| 微服务/云函数 | 服务拆分边界、通信协议、服务发现、部署单元 |

### 2.3 架构文档通用章节

所有类型都应包含：

```markdown
# 项目架构设计

## 一、架构总览
[分层图/模块图]

## 二、技术选型
| 层 | 选型 | 原因 |
|----|------|------|

## 三、模块职责与边界
[按类型模板填充]

## 四、数据模型（如适用）
[ER图 + 表/集合定义]

## 五、核心数据流
[2-4条关键流程的步骤序列]

## 六、错误处理策略
[各层的异常处理约定]

## 七、目录结构
[完整的项目目录树]
```

## Step 3：可行性分析与风险评估

**目标**：在架构文档末尾追加风险评估章节（或独立 `docs/feasibility.md`）。

### 3.1 四维评估

从以下维度逐一评估，输出高/中/低 + 应对策略：

| 维度 | 评估内容 |
|------|---------|
| **技术风险** | 选型技术是否有已知坑？外部 API 稳定性？跨平台/浏览器兼容问题？ |
| **数据风险** | 是否需要数据迁移？格式兼容？数据量大否？ |
| **资源风险** | 硬性截止日期？可投入工时？是否需要购买服务？ |
| **需求风险** | 哪些需求目前最模糊？可能变化的部分？ |

### 3.2 输出模板

```markdown
## 八、风险与应对

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| ... | 高/中/低 | 高/中/低 | ... |

## 九、假设与前置条件
- [列出设计中的所有假设，如"假设 DeepSeek API 可用"]
```

## Step 4：开发计划构建

**目标**：产出 `.qoder/plans/<项目名>_计划.md`，包含分阶段任务清单、测试策略、neat-freak 同步点。

### 4.1 阶段拆分策略

按「自底向上、逐层集成」原则拆阶段，**适用于所有项目类型**：

```
阶段0（必须有）：基础设施 — 项目骨架、依赖安装、构建/运行/测试脚本
阶段1（必须有）：数据层 — 数据库/存储初始化、数据模型、种子/测试数据
阶段2-N      ：按架构分层逐层向上 — 服务层 → API层 → 前端层 → ...
阶段收尾     ：集成测试、异常覆盖、文档同步、跨平台验证
```

阶段数量根据项目类型调整：
- **Web全栈**：通常5-6阶段（0→1→服务→API→前端→收尾）
- **CLI工具**：通常3-4阶段（0→核心命令→配置/UX→收尾）
- **库/SDK**：通常3-4阶段（0→核心API→文档/示例→收尾）
- **数据管道**：通常3-4阶段（0→连接器→转换→调度→收尾）
- **其他类型**：Agent 根据复杂度自行判断

### 4.2 每个阶段必须包含

```markdown
### 阶段X：<名称>（预计天数）

**目标**：一句话

**任务清单**：
- X.1 <任务名> → 产出：<文件/验证点>
- X.2 ...
- **X.99 neat-freak 同步 + git commit**

**测试策略**：
- 单元测试：[范围]
- 集成测试：[范围]
- 验证点：[关键确认项]

**并行可能性**：[哪些任务可并行]
```

### 4.3 neat-freak + git 纪律硬编码

每个阶段末尾**固定**包含：
```markdown
- X.99 执行 neat-freak 文档同步 + git commit（一句话中文总结本轮改动）
```

在计划文档开头加入总览提醒：
```markdown
> **纪律约定**：
> - 每个阶段完成后必须执行 neat-freak 同步 + git commit
> - git commit 格式：一句话中文总结本轮改动
> - 若待办项 ≥6，每完成 3-4 项后主动触发 neat-freak 上下文压缩
```

### 4.4 使用 create_plan 工具

计划构建完成后，调用 `create_plan` 工具（mode: write），将计划内容写入。用户后续可通过 plan 模式跟踪进度。

## Step 5：规则与文档索引建立

**目标**：创建 Agent 自治管理规则和项目索引文档。

### 5.1 创建两个 Always-On 规则

#### A. 项目阶段状态规则

创建 `.qoder/rules/项目阶段状态.md`：

```markdown
---
trigger: always_on
---

## 项目阶段状态（{当前日期}）

### 当前阶段
**第X阶段：{阶段名}** — {进度说明}

### 已完成阶段
- ✅ 阶段0：基础设施搭建 — {日期} — {一句话总结}

### 项目结构
[目录树，标注关键文件职责]

### 技术栈速查
| 层 | 技术 |
|----|------|

### 阶段开发流程
1. 开发 → 2. 测试验证 → 3. neat-freak 文档同步 → 4. git commit

### 关键参考文档
- `docs/architecture.md` — 架构设计
- `docs/requirements.md` — 需求文档
- `.qoder/plans/` — 开发计划
```

#### B. 长程任务上下文压缩规则

创建 `.qoder/rules/长程任务上下文压缩规则.md`：

```markdown
---
trigger: always_on
---
## 长程任务上下文压缩规则

适用场景：当前规划的任务列表中待办项 ≥6 项时，视为长程任务。

### 自动压缩策略

每完成 3-4 个待办项后，**必须主动执行一次上下文压缩**：

1. 调用 Skill 工具执行 neat-freak，触发记忆同步和文档一致性审查
2. 待 neat-freak 完成后，review 当前 todo 列表，确认进度和下一步目标
3. 用简短语言重新向自己确认：「当前已完成 X/Y 项，剩余任务为...」
4. 继续执行后续任务

### 目的
- 压缩已消耗的对话上下文，释放空间
- 将已完成工作的关键结论写入记忆，不至于丢失
- 保持 Agent 对剩余任务的清醒认知
```

### 5.2 创建项目索引文档

创建 `docs/index.md`，结构：

```markdown
# {项目名} - 项目索引

> 一句话定位 | 当前阶段：{阶段X 进行中/已完成}

## 目录结构
[完整项目目录树 + 关键文件说明]

## 技术栈
| 层 | 技术 | 版本 |
|----|------|------|

## {数据模型/API端点/命令}速查
[根据项目类型选择：数据表/API路由/CLI命令/...]

## 启动命令
```bash
npm install / pip install / ...
npm start / python main.py / ...
```

## 开发阶段
| 阶段 | 内容 | 状态 |
|------|------|------|

## 关键参考文档
| 优先级 | 文件 | 用途 |
|--------|------|------|
| 🔴 | docs/architecture.md | 架构设计 |
| 🔴 | docs/requirements.md | 需求文档 |
| 🟡 | .qoder/plans/ | 开发计划 |
```

## 完成标志

5步全部执行完毕后，向用户汇报：

```
✅ 项目初始化完成！已产出：
  - docs/requirements.md    — 需求文档
  - docs/architecture.md    — 架构设计（含风险评估）
  - docs/index.md           — 项目索引
  - .qoder/plans/*.md       — 开发计划（X阶段）
  - .qoder/rules/项目阶段状态.md
  - .qoder/rules/长程任务上下文压缩规则.md

下一阶段：阶段0 — 基础设施搭建。说"开始"即可启动。
```
